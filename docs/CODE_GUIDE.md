# Разбор кода для защиты IT Service Desk

## Как объяснить проект за полминуты

«Это приложение на Laravel для учёта обращений в техническую поддержку. Пользователь создаёт и просматривает свои заявки. Администратор видит общую очередь и меняет статус. Я разделил обработку запроса, работу с данными и вывод страниц по MVC. Валидация находится в Form Requests, проверка владельца в Policy, проверка администратора в middleware».

## Путь запроса на примере создания заявки

1. Браузер отправляет POST `/tickets` с полями формы и CSRF-токеном.
2. Маршрут из `routes/web.php` направляет запрос в `TicketController::store`.
3. Middleware `auth` проверяет вход. `StoreTicketRequest` проверяет допустимые поля и значения до вызова метода.
4. Контроллер вызывает `$request->user()->tickets()->create($request->validated())`.
5. Eloquent сохраняет запись. Связь `tickets()` задаёт автора из текущей сессии, а начальные статус и приоритет предусмотрены моделью и схемой.
6. Контроллер перенаправляет на `tickets.show`, где Blade выводит карточку.

**Почему нельзя передать чужой user_id?** Пользовательская форма не управляет автором. Запрос отклоняет запрещённые поля, а связь берёт ID вошедшего пользователя.

## Контроллеры

| Файл в app/Http/Controllers | Назначение методов |
|---|---|
| `AuthController.php` | `register` и `login` показывают формы. `store` создаёт обычного пользователя. `authenticate` проверяет учётные данные и обновляет сессию. `logout` завершает вход и обновляет CSRF-токен. |
| `DashboardController.php` | Единственный метод `__invoke` считает собственные активные заявки по статусам и передаёт последние записи в шаблон. |
| `TicketController.php` | `index` выводит список с пагинацией, `create` показывает форму, `store` сохраняет новую запись. `show` показывает карточку, `edit` форму изменения, `update` сохраняет изменения, `destroy` выполняет Soft Delete. |
| `ProfileController.php` | `edit` показывает профиль, `update` сохраняет имя/email/аватар. `password` проверяет текущий пароль и сохраняет новый хеш. Старый аватар удаляется после успешного обновления записи. |
| `Admin/TicketCrudController.php` | Настраивает операции Backpack: колонки, фильтр, счётчики, карточку и полную форму. Метод `update` явно присваивает проверенный статус и сохраняет заявку. |
| `Admin/TicketStatusController.php` | Единственный `__invoke` меняет только статус из формы в строке таблицы. Остальные поля заявки не затрагивает. |
| `Admin/CategoryCrudController.php` | Настраивает CRUD категорий. Проверяет использование категории перед удалением, включая мягко удалённые заявки. |
| `Admin/UserCrudController.php` | Настраивает список и карточку пользователей. Изменение ролей и паролей через эту панель не предусмотрено. |

**Что такое контроллер?** Класс, который организует действие по HTTP-запросу: получает проверенные данные, вызывает модель и возвращает HTML либо перенаправление. Его не следует превращать в файл со всем HTML, SQL и проверками сразу.

**Что такое `__invoke`?** Специальный метод для контроллера с одним действием. В маршруте достаточно указать класс контроллера.

**Почему в Backpack не видно всех методов CRUD?** Общие действия предоставляет пакет через traits `ListOperation`, `ShowOperation`, `UpdateOperation`, `DeleteOperation`. Методы `setup...Operation` настраивают эти действия. Наш `update` переопределяет сохранение полной формы заявки.

## Как работает смена статуса

1. `resources/views/admin/tickets/status-form.blade.php` выводит select и кнопку «Сохранить».
2. HTML-форма отправляет POST с `@method('PATCH')`: Laravel воспринимает его как PATCH.
3. Маршрут `admin.ticket.status` находится в `routes/backpack/custom.php` внутри защищённой административной группы.
4. `EnsureAdmin` и `UpdateTicketStatusRequest::authorize` проверяют роль. `rules()` допускает только ключи `Ticket::STATUSES`.
5. Route Model Binding находит `Ticket $ticket` по ID. Несуществующая или мягко удалённая запись возвращает 404.
6. `TicketStatusController` присваивает `$ticket->status`, вызывает `save()`, пишет техническую запись в лог и возвращает администратора к списку.

Статус исключён из `Ticket::$fillable`. Поэтому администратор присваивает его явно после проверки прав, а массовое заполнение пользовательских данных не может изменить его случайно. Список статусов: `new`, `under_review`, `in_progress`, `resolved`, `closed`.

Фильтр проходит проверку допустимости, затем `setupListOperation` добавляет условие к запросу. Этот же код выполняется для AJAX-загрузки DataTables. Счётчики рассчитываются отдельно для всех активных заявок.

## Модели, представления и база

- `app/Models/User.php`: пользователь, роль, профиль, связь hasMany с заявками.
- `app/Models/Ticket.php`: заявка, списки статусов и приоритетов, belongsTo с автором и категорией, SoftDeletes.
- `app/Models/Category.php`: категория, связь hasMany с заявками.
- `resources/views`: шаблоны Blade. `{{ ... }}` экранирует пользовательский текст. Директивы `@csrf`, `@method`, `@foreach`, `@if` помогают строить формы и вывод.
- `database/migrations`: версии схемы базы, создающие таблицы и ограничения. `up()` применяет изменение, `down()` откатывает.
- `database/seeders`: демонстрационные записи, не схема. Сидер нельзя путать с миграцией.
- `database/factories`: заготовки данных для тестов и сидеров.

Миграция `2026_10_04_000001_add_under_review_ticket_status.php` расширяет ENUM без удаления таблицы. При откате переводит `under_review` в `new`, чтобы старый ENUM принял значение. Остальные поля заявки сохраняются.

## Частые вопросы преподавателя

**Чем аутентификация отличается от авторизации?** Первая определяет, кто вошёл. Вторая проверяет, разрешено ли ему конкретное действие.

**Чем middleware отличается от Policy?** `EnsureAdmin` защищает целый административный раздел по роли. `TicketPolicy` проверяет доступ к конкретной заявке по её владельцу.

**Чем `authorize()` отличается от `rules()` в Form Request?** Первый проверяет право выполнить действие, второй допустимость отправленных данных. Проверка формы в браузере удобна, но не заменяет серверную.

**Зачем `with('category')`?** Это предварительная загрузка отношений. Она предотвращает отдельный запрос категории для каждой строки списка, то есть проблему N+1.

**Почему `$request->validated()`, а не `$request->all()`?** В сохранение попадают только поля, прошедшие правила проверки. Дополнительно модель ограничивает массовое заполнение через `$fillable`.

**Что происходит при Soft Delete?** Заполняется `deleted_at`. Строка остаётся в базе и автоматически исключается из обычных запросов. Интерфейс восстановления в текущем MVP не реализован.

**Зачем CSRF?** Сервер сравнивает токен формы с токеном сессии и отклоняет поддельный запрос с другого сайта. Сам токен не заменяет проверку прав.

**Как хранятся пароли?** В виде хешей Laravel. Открытый пароль не сохраняется в базе. При входе выполняется проверка соответствия, а не расшифровка хеша.

**Почему нельзя просто скрыть кнопку админки?** Скрытая кнопка не защищает URL. Поэтому запрет проверяется сервером и действует также для ручного PATCH-запроса.

**Какие проверки выполнены?** 44 теста и 226 утверждений на SQLite, затем такой же набор на отдельной MariaDB. В числе тестов есть доступ к чужим заявкам, смена статуса, недопустимые статусы и обратимость миграции. Один тест стандартный unit из skeleton, остальные 43 функциональные.

## Что открыть в редакторе на защите

1. `routes/web.php` и `TicketController::store`: простой путь создания записи.
2. `StoreTicketRequest` и `TicketPolicy`: валидация и права.
